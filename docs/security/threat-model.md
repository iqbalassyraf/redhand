# Threat model: Phases 1 through 3 (Identity and control; Stop things; See things)

**Last updated:** 2026-11-07. Update this file whenever a trust boundary changes (CLAUDE.md §5.1).

## 1. Components and trust boundaries

```
 Operator browser ──(1) Supabase JWT──▶ redhand-core ◀──(3) service token── AgentWall gateway
                                         │  ▲                                  │      ▲
                                         │  └──(2) agent key → access token ───┘      │
                                         ▼                                            │
                                  Postgres (Supabase)              Agent ──(4) access token
                                                                                      │
                                                     customer MCP server ◀──(5) HTTPS─┘
```

| # | Boundary | Authentication | Notes |
|---|---|---|---|
| 1 | Operator → core | Supabase access token (ES256/RS256 via JWKS, or HS256 with a shared secret; `aud=authenticated`), tenant and role from `organization_members` | All control actions authorized server-side |
| 2 | Agent → core (token exchange) | Agent key (256-bit, stored hashed) | Refused unless passport active; rate-limited per key |
| 3 | Gateway → core (`/internal`) | Shared service token, constant-time compare | Missing token means every agent call is denied |
| 4 | Agent → gateway | Ed25519 access token, 10 min, verified with public key | Plus per-call passport status check (≤ 2 s cache) |
| 5 | Gateway → MCP server | Optional upstream credential supplied by the agent | Destination check per request: https, public IPs, no redirects |
| 6 | Telegram → core webhook | Secret header (constant-time compare), then the chat must be linked to an operator whose role is re-read on every command | Public endpoint by necessity; private chats only; stop-only commands (ADR 0008) |
| 7 | Gateway → core (`/internal/v1/events`) | Shared service token, constant-time compare (same boundary as #3) | Each batch claims one organization; every item's agent is re-checked against that organization inside `record_events()` (ADR 0011) |
| 11 | Gateway → core (`/internal/v1/tool-observations`) | Shared service token, constant-time compare | Tool versions only (hash, capped text, rule ids); server and organization re-checked in SQL |
| 10 | Core → gateway (`/internal/v1/scan`) | Shared service token, constant-time compare | The URL is a registered server of the caller's organization chosen by core; the gateway re-checks the destination before sending |
| 9 | Gateway → core (`/internal/v1/trips`) | Shared service token, constant-time compare | Identifiers only; every claim re-checked in `record_trip()` (same boundary family as #3 and #7) |
| 8 | Operator → core (`/v1/blackbox/*`) | Same as #1 | Timeline, verify, payload view and export all filtered by the caller's organization_id in SQL |

## 2. Threats and mitigations

| Threat | Mitigation | Residual risk / follow-up |
|---|---|---|
| Hijacked or prompt-injected agent calls tools outside its job | Passport scopes enforced per `tools/call`; `tools/list` filtered; SQL/shell guardrails; resources/prompts methods refused | Read vs write is enforced only in Safe Mode, and only as declared by the operator (ADR 0009) |
| Stolen agent access token | 10-minute lifetime; freeze/revoke denies within ≤ 2 s via status lookup | Token usable until revoked if theft is undetected |
| Stolen agent key | Revoke or rotate deactivates it immediately; only hash stored | No anomaly detection on key use yet |
| Agent bypasses the gateway with raw upstream credentials | Out of scope by design; product copy states the limit | Credential broker (Phase 1.5) closes this |
| Malicious or compromised MCP server | Response size and time limits, no redirects, secrets redacted from tool results, unsupported methods refused | Poisoned tool descriptions not yet scanned (Phase 4) |
| SSRF through registered MCP server URLs | Registration: https and public host; per request: resolve then require public addresses | DNS rebinding between check and connect (pin connection to checked IP) |
| Cross-tenant access | Tenant from verified membership; every core query filtered by organization; gateway context bound to token's tenant; SSE stream filtered | core uses service role, so isolation relies on core's queries (RLS is defense in depth) |
| Forged operator identity / spoofed headers | No identity headers are trusted; reviewer is the authenticated operator; operator tokens are verified as ES256/RS256 against the project's JWKS (or HS256 with a shared secret), never both; HS256 is rejected in JWKS mode (no algorithm confusion); issuer, audience and expiry are checked (ADR 0007) | A signed-out operator's token stays valid until it expires; shorten the Supabase access-token lifetime |
| Insider or compromised admin abuses control actions | Role requirements (revoke, freeze-all, scope expansion need admin), explicit confirmation, append-only audit with actor and reason | No step-up authentication yet |
| The dashboard's Insights summary (`GET /v1/insights/summary`) leaks another organization's activity, or shows zeros when a read failed | Viewer role and above; the organization comes from the operator's login, never the request; the SQL function filters on it and is callable by `service_role` only; only aggregates are returned (no argument, payload or captured text) and refusal reasons are mapped in SQL to a fixed set of categories, so no tool, server-argument or address text from a refusal sentence appears; window and bucket are mapped from three allowed values and bounded again in SQL (at most 8 days, 60 buckets); a failed or malformed read is a 503, never a zero (sweep test and a mutant on the organization filter) | Names of agents, servers and tools and the gateway's reason strings are visible to every role in the organization, as in the Black Box events they come from |
| Operator sign-in through Clerk (ADR 0032): a forged, replayed or foreign token, an account takeover by claiming an e-mail, a token stolen from the browser | RS256 only, our own audience (`redhand-core`), the Clerk instance as issuer, `exp`/`nbf`, a verified e-mail required; the person is mapped to RedHand's own operator id and is never matched to an existing account by e-mail; roles and tenants stay in our database; unreachable keys or a database failure deny; the dashboard keeps the token in memory only and renews it before it expires; the CSP allows only the Clerk instance, its image host and the bot challenge; Supabase and shared-secret tokens are refused in Clerk mode | A Clerk-side compromise or a misconfigured template (for example a wrong `aud`) is the identity provider's trust boundary; a token stays valid until its lifetime ends after sign-out (set the template to the shortest the owner accepts, 10 minutes recommended) |
| Audit tampering | `control_audit_log` and the Black Box's `agent_events` are blocked from UPDATE/DELETE by trigger; the Black Box is hash-chained per organization and verifiable (`GET /v1/blackbox/verify`). The gateway keeps no ledger of its own (ADR 0030) | While core is unreachable for longer than the gateway's bounded buffer, decisions are dropped and counted (`recorder.gap` marker, metric), though every call is still enforced; a core operator with database owner rights could rebuild the chain (the append-only trigger stops application code, not the owner) |
| Audit gap after a control action | Each action and its audit row commit in one database transaction (`control_*` functions); a failed audit write rolls the action back. See ADR 0006 | A network timeout after commit leaves the outcome unknown to the caller (the API says to reload; actions are safe to repeat) |
| Stolen or lost phone with the panic command | Stop-only commands: it cannot unfreeze, revoke or widen scopes; admins can unlink a chat in the dashboard; every action is audited with `via Telegram` | The holder can freeze every agent (a denial of service, by design); no PIN on top of Telegram's own lock |
| Forged Telegram webhook calls | Secret header compared in constant time; a wrong secret does nothing and returns 401; unlinked chats get no information beyond "not linked" | Anyone who learns the webhook secret can send updates, but still needs a linked chat id to act |
| Attacker links their own chat | Link codes are created only by a signed-in admin or owner, are single use, expire in 10 minutes, stored hashed, with about 49 bits of entropy and 5 attempts per minute per chat | A code shown on screen can be shoulder-surfed within its 10 minutes |
| Replay of an old command | Update ids are claimed once in the database; the secret header is required | Freeze commands are idempotent anyway |
| Bot token leaks through logs | httpx request logging disabled in the Telegram module; errors logged by class only; tests assert the token is absent | A future logging change elsewhere could reintroduce it: the test covers the module only |
| Removed or demoted operator still has a linked phone | Role and membership are re-read per command; unlink revokes the link | None known |
| Agent keeps writing during an incident | Safe Mode (agent or organization): the gateway allows only read-declared scopes; on within about 2 s; audited; ON from a phone, OFF only by an admin in the dashboard (ADR 0009) | RedHand cannot verify a tool is read-only: the declaration is the operator's. A `*` scope declared read covers the whole server. |
| Safe Mode silently skipped after a version mismatch | The gateway requires `safe_mode` to be a real boolean from core; otherwise it denies. Core reads anything but a stored `false` as ON | An old gateway ignores the flag: deploy core first and enable only after both are updated |
| Runaway or hijacked agent does unbounded work | Budget Guard: a daily cap on forwarded tool calls enforced in the gateway with no I/O on the decision path; alerts at 80% and 100%; optional auto-freeze (ADR 0010) | Counts calls, not cost or LLM spend. Agents with no limit are never stopped. With several gateway instances the cap can be exceeded briefly (bounded and documented). |
| Limits relaxed without authority | Raising or removing a limit, or turning auto-freeze off, needs an admin and confirmation; the change is compare-and-set against the state the decision was made on | None known |
| Forged or inflated usage reports | `/internal/v1/usage` needs the internal service token; the organization comes from the agents table; counts are monotonic and bounded; at most 1,000 items per report | A compromised service token could inflate counts and block an agent for the day (raise its limit to recover) |
| Budget silently skipped after a version mismatch | The gateway requires a strictly typed `budget` from core and denies otherwise; a malformed stored limit reads as 0 | An old gateway ignores the field: deploy core first |
| New agents start unprotected | Optional organization default daily limit applied at registration (audited, best effort); only an admin sets it, and raising or removing it needs confirmation; the dashboard flags agents with no limit | If applying the default fails the agent has no limit until someone sets one; the default is off until an admin turns it on |
| Core outage | Gateway fails closed (denies) | Availability target 99.9 %; no multi-region yet |
| Signing key compromise | Ed25519 private key only in core; gateway holds public key | Signing-key rotation not automated |
| Development shortcuts reach production | core refuses the in-memory store and `/v1/dev/login` outside development; signing key required outside dev/test; no hardcoded secrets | Deployment checklist must set all required secrets |
| Supply chain | Locked dependencies (`uv.lock`, `package-lock.json`); no new packages added in Phase 1 (pyjwt was already locked) | No automated vulnerability scan in CI yet |

| Recorded event forged or injected into another tenant's chain | `record_events()` derives each item's organization from the agents table, never from the gateway's claim; a mismatch is rejected, not written | A compromised gateway instance with a valid service token could still write junk events into its own tenant's chain (visible as odd entries, not a cross-tenant leak) |
| Black Box events read by the wrong tenant | `/v1/blackbox/events` and `/v1/blackbox/verify` scope every query by the authenticated operator's `organization_id`; tested for cross-tenant timeline and verify | None known |
| Stored event tampered with after the fact (e.g. direct database access) | Append-only trigger refuses UPDATE/DELETE outside the purge path; `verify_events()` recomputes the chain and reports the first seq that does not match | Someone with database superuser access could still rewrite the whole chain; external anchoring of the chain head is a tracked follow-up (Phase 3 plan, decision D4) |
| Recorder outage or flood used to hide activity | Buffer overflow drops the newest events (not silently): a `recorder.gap` marker is recorded once flushing resumes, and `redhand_gateway_events_dropped_total` is a metric | A sustained flood that keeps the buffer full could delay gap reporting; Budget Guard already caps an agent's own call rate |
| Black Box events erased to hide activity, using the application's database access | Append-only trigger: deletes only behind the retention anchor, updates only clear payloads. Anchor guard: moves only forward, onto a real event's hash, older than the retention (min 7 days). Purges and retention changes are audited | A superuser can bypass triggers; lowering retention to 7 days (audited, admin, confirmed) then waiting for the purge erases older events |
| Captured payloads expose personal data or secrets (M2b) | Off by default; turned on only by an admin with confirmation, audited; the gateway redacts secrets, personal-data patterns and sensitive field names BEFORE truncating to 2 KB and never stores unscanned text; the database enforces the flag; payloads are kept 7 days by default and never returned by the timeline API or written to logs; any failure records the event without a payload | Names, addresses and free text are not detected, nor numbers split across fields; core trusts the gateway's redaction and does not re-scrub, so a compromised gateway instance could send unredacted text (the gateway already holds the raw payload in memory); a value over 16 KB is not captured |
| Captured payloads read or exported by the wrong person (M2c) | Viewing a payload and exporting payloads need the admin role, metadata export the security operator role; both checked in the router and the service, scoped by organization in SQL; each read is audited in the same transaction as the read (actor and seq, never the text) and each export is audited before the first row; per-operator rate limits; exports capped at 50,000 rows and streamed; `Cache-Control: no-store`; CSV formula injection neutralised; the dashboard renders payload text as plain text and shows only the controls the server says the role may use (cosmetic: the server decides); admins can delete all captured payloads at once (confirmed, audited with the count) | A compromised admin account can read and export captured payloads (audited, rate-limited, capped, not prevented); limits are per core instance; redaction limits still apply to what is exported |
| Agent uses or reads planted bait (Phase 3 M3/M4) | Honeytokens: values generated server side, shown once, stored as SHA-256 only; the gateway holds digests only and matches by lookup (no I/O); a call carrying bait is refused before upstream, bait in a result is redacted, a decoy tool is never forwarded; the context fields are required (an older core makes the gateway deny); a scanner error denies; core re-checks the agent and reference against the organization and decides the action from what it stores; trips are idempotent, audited as the system actor, alerted (value never included) and, per the stored action, freeze the agent | Exact-match detection on three issued formats: a re-encoded, split or beyond-64-KiB value is not found; a freeze takes effect on the next call after core processes the trip (at most about 4 s of context cache); a compromised gateway instance holding a valid service token could send false trips (they alert or freeze an agent of its own tenant, visible in the audit) |
| Prompt leak through tool calls or results (Phase 4 M5a) | A `canary` honeytoken pasted into the system prompt: an exact digest match in arguments (call refused) and results (redacted); alert says the prompt text "appears to have leaked"; defaults to alert, never freeze | Only the gateway's view: not a prompt shown to a person or sent to a model provider; a re-encoded, split or glued value is not found; a legitimate agent that passes its instructions to a tool trips it |
| Canary replayed on purpose to spam or freeze an agent (Phase 4 M5a) | The default action refuses and alerts but never freezes; freezing is an explicit admin choice; alerts are limited to one per agent and canary per 5 minutes; every trip is audited | An admin who chooses freeze lets anyone holding the prompt freeze that agent on demand; the page and runbook say so |
| Honeytoken value exposed | Never logged, never in events, alerts, audit rows, list responses or the context; no payload is captured for a trip; creation responses are `no-store` | The value is visible to the person who creates it, and to anything they paste it into |
| Trip flood used to spam or freeze | One alert per agent, bait and place per 5 minutes; 50 reports in flight at most; the report endpoint needs the service token | A flood of real trips still freezes that agent (by design) |
| Poisoned MCP tool description hijacks an agent (Phase 4 M2) | Description rules (hidden instructions, concealment, exfiltration, cross-tool coercion, invisible characters) in the manifest auditor, English and Bahasa Malaysia, with text normalisation against obfuscation; findings never repeat the description; measured on a held-out set | Pattern rules miss rephrased attacks (first held-out detection 12 to 13 of 20); only the first 8 KiB of a description is read for phrases (length is flagged); a server that changes after approval is not caught until tool pinning (M3) |
| Live scan used to make RedHand fetch an internal address | Registered servers only (organization-scoped in core, URL from the database, never the request); fetched by the gateway through the agent-traffic destination check (https, public addresses, no redirects, size and time limits, 5 pages, 500 tools); admin role; 20 scans a minute; service token on the gateway endpoint; results not stored | DNS rebinding between the check and the connect (same residual risk as agent traffic) |
| Scan result carries an attack to the admin reading it | Server text is reduced to name, description and schema, stripped of control and invisible characters and length-capped in core; findings quote rule wording only; the dashboard renders plain text | A tool name (up to 128 characters) is shown as plain text |
| MCP server changes a tool after the owner approved it ("rug pull") (Phase 4 M3) | Each tool version is hashed (name, description, schema) when listed through the gateway and reported to core as pending; the owner approves or rejects in the dashboard; changes alert (counts only); enforce mode hides and refuses tools whose current version is not approved, and fails closed if it cannot check; core denies via 503 if it cannot read the approved list | Only seen when an agent lists tools through the gateway; a tool that behaves differently under an unchanged description is not caught; a tool never listed through the running gateway process is judged by name alone in enforce mode; a change reaches enforcement at the next context refresh (a few seconds) |
| Tool pin data abused (flooding or injection through descriptions) | Caps: 200 tools per report, 500 tools per server, 20 versions per tool, 2,000 and 8,000 characters of description and schema; versions keyed by hash so repeats cost nothing; alerts at most once per server per ten minutes and never include tool text; text shown as plain text; organization and server re-checked in SQL on every call | A malicious server can fill its own 500-tool quota with pending versions (visible, bounded, removable by deleting the server) |
| Black Box recorder outage affects enforcement | `EventRecorder.record()` does no I/O and never raises into the decision path; flush failures only grow the buffer | None known |
| Operator password reset abused (account takeover or user enumeration) | The reset request answers identically whether or not the account exists; the link is Supabase's own one-time token, delivered in the URL fragment (never sent to a server or in a Referer header) and removed from the address bar on load; the new password is 12 to 128 characters; a successful change signs out every session of that user; redirect targets are limited to the Supabase redirect allow-list; email sending is rate-limited by Supabase. Not covered: a compromised mailbox (no second factor on the reset yet). |
| Radar suppression or mode change used to blind the checks (insider or compromised admin) (Phase 4 M4.2) | Admin role only; turning a check off and every suppression need `confirm: true`, a reason for suppressions, and are audited (actor, rule, agent, days); a suppression is for one rule on one agent, 1 to 90 days, expires by itself, is capped at 100 live per organization and is listed on the Radar page; only Radar rule ids can be suppressed (never a honeytoken check); block mode is refused until the measured gate exists. |
| Radar findings used to flood storage or carry an attack to the reader (M4.2) | A finding is validated against fixed vocabularies in the API and again in SQL (rule id pattern, enumerations, evasion allowlist, capped tool name), so no scanned text can be stored; findings coalesce per agent, rule, tool and 5 minutes; at most 20 items per report and 2,000 new rows per agent per 24 hours; 90 days retention; organization and agent ownership are re-checked in SQL; the internal endpoint needs the service token. |
| Radar evasion by presentation (M4.1b): a documentation-style header on an address or path payload, a code span around markup, rephrasing, padding past 16 KiB | Recorded, not hidden: the header and code-span rules only lower a finding to low confidence (still stored and visible, never alerting), live markup and the injection rules ignore the header, any hidden or encoded evasion keeps its confidence; the limits are published in the coverage matrix and the plan; block mode needs the measured gate. Not covered: a rephrased attack, an attack buried mid-way in a very large result. |
| Radar quieter rules (M4.7b): an attacker shapes a payload like documentation (a plain role-word heading, a link or diagram label, a code-fence tag) so a rule reads it as documentation | A heading alone is weak but any payload cue (override, call, risky action, reveal, exfiltrate, address-the-agent, conceal, authority) keeps it strong, the stronger sighting always wins, a bracket directive that carries a call still fires, an inline command still fires; each class has a quiet test and an attack test; the cost is measured, not assumed (`docs/security/m4-7b-results.md`: tuning set 29% to 5%, frozen set 15.8%, target of 5% not met); the independent check is blind round 4, not yet scored | Detection can fall: a payload with none of the cues placed under a plain heading gets a low finding from that rule; no loss on the corpus or on round 3. Radar stays observe-only |
| Radar in the gateway turned against availability or the call path (M4.3): a hostile tool returns huge or crafted results to slow the scanner, flood core, or crash the worker | The scan runs on a bounded background queue (16, newest dropped and counted), never inline; it reads at most 16 KiB from each end, 1,000 nodes and depth 16; a repeat of the same finding is reported once per 30 s per process and core coalesces and caps (2,000 rows per agent per day); a scanner or reporter error is swallowed and counted and the worker survives; the Radar makes no decision, so no failure can allow or deny a call; the result is never modified. Residual: the scan competes for CPU with the gateway (measured, not yet on staging). |
| Radar self-test used to burn gateway CPU, to learn which held-out samples the rules miss, or by someone without the right (M4.5b) | The gateway route needs the service token and takes no input at all; one run at a time per process (a second is refused, not queued), at most about 60 ms of work on a worker thread; core allows a security operator or above and one run per organization per minute, counted before the call so a failing gateway is not hammered; the result is counts only, with no sample text and no sample ids, so held-out misses cannot be read off and tuned against; core validates the gateway answer strictly and a failure or malformed answer is an error, never invented numbers. Residual: the minute limit is per core instance (in memory), like the other limiters. |
| Radar evidence counts forged, inflated or flooded to make a check look ready for blocking, or to hide false alarms (Phase 4 M4.6b) | The counts route takes the service token only (same as findings), validates every field strictly (fixed vocabularies, numeric limits, consistency: flagged <= scanned, strong <= flagged), skips an invalid item whole in SQL and counts the skip, never stores text, and a report id makes a retried or replayed report count once. Counts are taken in the gateway before suppressions and the repeat limit, so an admin's silence cannot hide a result, and a silence live at any time in the 7-day window disqualifies the evidence. False alarms are counted the hard way (a reviewed false alarm marks every strong flag of its rule). A gap between stored findings and counted flags (counts lost) fails the readiness check. Readiness is display only and unlocks nothing: block mode is refused in SQL, core and the gateway. Residual: someone with the service token can still add counts; an admin who marks every finding "real" improves the figure (audited, and nothing is unlocked). |
| Readiness figures used to over-claim protection in the dashboard (M4.6b) | The panel says blocking is not available, labels a passing check only a "candidate", links to the independent tests, and the dashboard refuses any readiness or coverage data that claims blocking is available. Counts say nothing about attacks the checks cannot see. |
| Second-stage injection model abused (M4.1c): tampered or poisoned weights, adversarial rewording, resource exhaustion, a broken file | The model is a plain JSON data file reviewed in a pull request (no pickle, no code), size-capped, with a parity test that a tampered file would fail and a deterministic retrain check; training samples enter only through reviewed pull requests; only a score of 0.9 or more is actionable and the model is not offered a block mode; a missing or malformed file makes the stage report nothing and never affects scanning or enforcement; work is bounded (48 windows, 16 KiB) and planned for a background queue, never the call path. Not covered: text the model has not seen (rewording), calibration shifts between authors. |
| Secret scanner (`redhand scan`, M5b) leaks the secrets it finds: a value in the console, in a CI log, in a SARIF report or in an error | A finding has no field for the value, every message comes from a fixed table, errors name the path and the reason only, and a test plants a value of each kind and searches stdout, stderr and the SARIF text for any part of it. The help text and the runbook say a found secret must be rotated, because git history keeps it |
| Secret scanner turned against the machine that runs it (a hostile repository): symlinks to private files, huge files, endless folders, regular-expression blow-up | Symlinks are not followed or read; files over 1 MiB are skipped, not partly read; at most 5,000 files and 50 findings per file; the patterns are linear and a test scans 1 MiB lines in a time limit; the scan makes no network call. A file it cannot read is counted as skipped, never silently ignored |
| A clean `redhand scan` read as proof that no secret exists (M5b) | The clean message says it is not a guarantee and the help text lists the file types and key formats it checks. It is still a partial check: passwords, database URLs, custom tokens and encoded values are not found |
| An agent stuck in a loop, or a prompt-injected instruction to repeat, burns the daily budget and hammers a customer system (Phase 4 M6) | The gateway counts identical calls per agent (salted digest of tool and arguments, never stored or sent) and flags the limit-th repeat in a window (default 20 in 60 s). Observe (default) records and alerts; throttle also refuses the repeat before it can use budget. A call that changes its arguments each time, calls made outside the gateway, and the extra limit with several instances are NOT covered, and the dashboard, runbook and ADR 0017 say so |
| Throttle used to disrupt an agent, or the loop settings changed by the wrong person (M6) | Only an admin can change the mode, limit and window, throttle and off need an explicit confirmation, every change is audited with the actor (`organization.loop_settings_changed`) and compare-and-set stops two admins overwriting each other. A hijacked agent has no access to core, and a third party can only cause a throttle by making that agent repeat the same call, which is the behaviour being limited. The refusal message carries counts only, never arguments. Any meter error in throttle mode denies; the gateway-wide kill switch (`AGENTWALL_LOOP_DETECTION_ENABLED`) skips the meter |
| Loop meter memory exhaustion or evasion by an attacker-controlled agent (M6) | Each key holds three numbers; at most 16 keys per agent and 100,000 in all (about 20 MB), tested with 20,000 agents and with 1 MiB arguments inside a time limit. At the cap the oldest key is dropped, so a loop may be missed under extreme pressure: this is a detection control, so it errs toward under-counting and is counted in `redhand_gateway_loops_total{outcome="evicted"}`. Arguments that cannot be serialized are not counted (`untracked`) |
| Risk Engine (Phase 4.5 B1) used to freeze or restrict the wrong agent: a hostile agent or tool tries to raise ANOTHER agent's score, or noisy rules push good agents over an opted-in rung | Signals are counted per agent and per organization in SQL (no cross-agent input); automatic Safe Mode and freeze are off by default and need an admin with a confirmation; open Radar findings weigh 4 points (capped at 16), so the noisy rules alone never reach a rung; false alarms and silenced rules count zero; the card names the agents each rung would act on now; every action goes through the existing audited control functions and is announced | A wrong weight in an opted-in organization can still freeze a good agent: it is announced, audited and reversible, and the release rule stops a loop |
| Risk Engine turned against availability or the report path: a flood of reports makes core re-score constantly, or a slow scoring query delays the gateway's reports | Scoring runs only for agents named in a report (a Black Box batch only for agents with a refusal), bounded to 5 seconds, and never fails the report; one indexed aggregate per agent (5 to 7 ms locally with 70,000 rows); the gateway's call path is untouched | Heavy report traffic costs core CPU; there is no per-organization budget on evaluations yet |
| Risk Engine overturning a person's decision: an agent is unfrozen and the same evidence freezes it again, or the score is read as a guarantee | A trigger stamps every human release; only later signals count towards automatic actions; the page and runbook say the score is judgement, not a probability, and only covers agents connected through RedHand | None beyond the stated limits |
| Behaviour baseline (Phase 4.5 B2) evaded or abused: an agent changes slowly so its baseline follows it, acts during its first 7 days, or a flood of tool calls inflates the roll-up | Watch-only (no points, alert or action), so a wrong verdict cannot restrict anyone; counts per agent and organization (no cross-agent input); every verdict shows a back-test so a noisy agent is visible as noisy; the roll-up stores counts and tool names only, kept 35 days, service role only; the roll-up trigger shares the Black Box transaction, so a failure retries the batch instead of losing it | Slow drift and the warm-up period are blind spots by design (stated on the page); adds about 0.05 ms per event to Black Box ingest |
| A webhook URL (a Slack incoming-webhook URL, a resume URL with a token) leaks through logs or error text (H1.2) | Every log site logs the host and the error's type and HTTP status only (`safe_log.py`), because httpx repeats the URL in its own message; tests read the log with a fake secret in the URL, and a static test fails if any log call mentions a `*webhook_url` unreduced | Third-party libraries could log a URL themselves: not audited here |
| The gateway runs out of memory through its own audit chain, or its audit file blocks requests (H1.3) | The in-memory chain is bounded (10,000 records) with the dropped record's hash as an anchor, so the window still verifies; file writes go to a writer thread and a failing disk is counted, not raised; the verify answer states the window | The in-memory chain no longer proves records older than the window: the Black Box is the complete record |
| Core is turned into a request forger (SSRF): a customer-supplied webhook URL (resume, Slack, SIEM) points at an internal or metadata address, a name that resolves to one, or redirects to one (H2.1) | One guard for every outbound webhook (`net/outbound.py`): https only, no credentials, no local or internal names, one DNS lookup with every answer required public (IPv4-mapped IPv6 unwrapped), the call goes to the checked address with the original Host and TLS name, no redirects, a total deadline, a response cap, URL-free errors; refused at ingest and again at send time; a refused URL is never retried and is counted | An address that becomes private after the check is not a risk here (the call goes to the checked address); a public host an attacker controls can still receive the data core sends it (that is the webhook's job) |
| DNS rebinding at the gateway: an MCP server name answers with a public address for the check and a private one for the connection (H2.2) | One lookup per call; the connection goes to a checked address with the original Host and TLS name (certificate still verified against the name); a failed connection moves to the next checked address, never a new lookup; kill switch `UPSTREAM_PIN_ENABLED=false` keeps the check | With the kill switch off the old window returns: it is for an emergency, not a setting |
| A slow or endless upstream response holds gateway capacity (H2.4) | One deadline covers the lookup, every attempt and the body; the response is size-capped | The deadline is `UPSTREAM_TIMEOUT_SECONDS` (30 s by default) per call, not per read |
| One client makes core or the gateway buffer an arbitrarily large body (H2.3) | A global body cap counted as the bytes arrive (1 MiB; 16 MiB on the two batched ingest routes); the gateway stops reading at its limit; a declared length over the limit never reaches a handler | Limits are per request, not per client: abuse across many requests is a rate-limit question (H3) |
| A development-only switch is left on in staging or production (H2.5) | Core refuses to start with `ALLOW_INSECURE_MCP_URLS` or `ALLOW_INSECURE_WEBHOOK_URLS` unless `ENVIRONMENT` is development or test; the gateway trusts only a known local environment name for `ALLOW_INSECURE_UPSTREAMS`, so a typo fails closed | A deployment that forgets to set the environment name at all gets the default `development`; the deploy script sets it |
| Script injection or data exfiltration from the dashboard through an XSS slip, framing (clickjacking) or MIME sniffing (H3.1) | A nonce-based Content-Security-Policy (no inline script, no eval in production, no framing, `connect-src` limited to this site, core, the gateway and Supabase), `nosniff`, HSTS, referrer and permissions policies; checked in a real browser on every page, three roles, two widths | Styles allow inline (they cannot run code); the access token lives in sessionStorage, so any script that does run can read it (tracked: httpOnly cookies) |
| A browser or proxy caches an authenticated answer, a token or a tool result (H3.2) | `Cache-Control: no-store` on every core and gateway answer unless the route chose its own; `nosniff`; HSTS | A route that sets its own caching (the event stream) keeps it |
| A caller steps round a per-address limit by forging `X-Forwarded-For`, or one proxy address becomes everyone's bucket (H3.3) | The address is read from the right by a trusted hop count (Cloud Run: 1), never uvicorn's leftmost-entry `*`; too few or unreadable entries share the proxy's bucket (over-limits, never evades); a test forbids `forwarded-allow-ips` in deploy | Correct only while the real number of proxies is the configured one; the night test (L6) proves it on the real platform |
| Memory exhaustion by sending a new key or address with every request (H3.3) | Both limiters are bounded (10,000 keys, idle swept, least recently used dropped); token exchange is limited per address before any hash or database read | Limits are per instance (single-instance deployment) |
| A leaked or guessed HS256 operator secret signs in as any operator in any organization (H3.4) | Refused outside development and test; shared environments verify asymmetric keys only (JWKS, ES256 or RS256) | A deployment on a legacy shared-secret project must migrate before it starts |
| A vulnerable dependency ships unnoticed (H3.5) | `pip-audit` and `npm audit --audit-level=high` fail CI; weekly grouped Dependabot; the first run found and fixed a high PostCSS advisory | Advisories published after the last run; GitHub Actions are pinned by tag, not commit SHA (follow-up) |
| A token that leaked or was issued before a freeze, an expiry change or a scope change keeps working once the passport is active again (H4.1) | The gateway refuses a token older than the passport version (`token_stale`) after the status check; a frozen or revoked agent is still reported as such; kill switch `TOKEN_VERSION_CHECK_ENABLED` | A token issued at the current version works until it expires (minutes) or the passport changes; a token is still a bearer credential |
| A rug-pulled MCP tool (an approved tool whose description or schema changed) is trusted on a gateway instance that never listed it (H4.2) | In Enforce mode the gateway looks the tool up on first use (bounded, shared, 10 s deadline, failed checks paused) and judges its current version; if it cannot be established the call is refused; kill switch `STRICT_PINNING_ENABLED` | A change made after the first lookup is caught at the next listing, not mid-session; a server that returns different tool lists per credential is judged on what this agent's credentials see |
| A server leaks a credential, a connection string or planted bait through a JSON-RPC error instead of a result (H4.3) | Errors get the same secret redaction and honeytoken check and trip as results; a scanner failure denies; kill switch `REDACT_UPSTREAM_ERRORS_ENABLED` | The redaction patterns are the egress guard's: a secret in a format they do not know passes |
| The incident view (Phase 4.5 B3) leaks another tenant's records or call contents, or is read by a role that should not | Every read is scoped by the caller's organization in the service, and by the agent where the record names one; another organization's agent is 404; a row naming the agent under another organization never appears; viewers get 403; items carry only the fields each screen already shows (no payloads, argument values, token ids, honeytoken values or audit details); tested with planted secrets and full hosts | Anyone with the security operator role sees every agent's story in the organization, as on the other screens |
| The incident summary export is used to bulk-copy an organization's history, or opened in a spreadsheet that runs injected formulas | Security operator and above, 10 per hour per operator, at most 5,000 items, audited before anything is read (no export without the audit row); CSV formula cells defused | Limits are per instance; an export is a copy outside RedHand once downloaded |
| A Telegram alert link is used for phishing or leaks data | The link is built only from the configured `DASHBOARD_URL` (plain https, no credentials, query or fragment, validated at start) and the agent id; it opens the dashboard, which still requires sign-in | The agent id is visible to whoever reads the owner's Telegram chat |
| Malformed numbers or over-deep JSON at the gateway edge, including before authentication, used to cause errors or reach the upstream forwarder (found during M6) | The edge parser refuses the non-JSON tokens NaN, Infinity and -Infinity, numbers that parse to infinity (`1e999`), integers of more than 4,300 digits and bodies nested too deep, and treats them as an unparsable body (answered after authentication, a 400, nothing forwarded). The forwarder encodes the message itself and turns an unencodable one into an upstream error. A catch-all around `handle()` turns any other unexpected error into a generic JSON-RPC deny (503, no cause shown) and counts it (`reason="internal_error"`). Tests cover each case and 13 deliberate breakages |
| Exfiltration: a hijacked or prompt-injected agent sends customer data to an attacker's address through a legitimate tool's arguments (Phase 4 M7) | An optional per-agent allowlist of exact hosts. The gateway reads the web and email addresses written in a call's arguments (values and keys) and, in enforce, refuses any outside the list, before the loop check and Budget Guard. Not covered, and stated in the dashboard, runbook and ADR 0018: an address written as a bare word, encoded, split across fields or built by the tool; what a tool does with the data; calls outside the gateway; scheme and port are ignored |
| Allowlist bypass by parser differences or look-alikes: userinfo (`good.com@evil.com`), backslash, fragment, encoded `@`, punycode homographs, IPv4 as one number, hex or octal, IPv6 and mapped addresses, trailing dots, case (M7) | One URL yields a set of candidate hosts (strict and browser readings, first and last `@`) and every candidate must be on the list; an unparseable candidate is never allowed; hosts are normalized (percent once, NFKC, IDNA, own IPv4 parser, IPv6 folding) with a copy in core guarded by a shared vector file and a source-equality test. Over 150 test cases plus a seeded fuzz, and 29 deliberate breakages, all caught |
| Allowlist widened or enforcement switched off by the wrong person, or locked into refusing everything (M7) | Admin only; adding a host, turning enforcement on and turning the check off each need a confirmation; every change is audited with the actor and host; the mode change is compare-and-set; enforce needs a non-empty list and the last host cannot be removed while enforcing; 100 hosts per agent and tenant checks are enforced in SQL. A hijacked agent has no access to core. A compromised admin can still widen a list: the audit log and dashboard show it |
| Scanner abused for CPU or evasion by an agent-controlled argument (M7) | Bounded work (64 KiB of text, 1,000 values, depth 16, 200 matches, 50 distinct destinations per call; no DNS); whatever is past a bound is `untracked` and refused in enforce, so it is never allowed unread. Measured: hostile 64 KiB inputs cost about 5 ms (they cost up to 31 ms before the match cap). Findings keep only the last two labels of a host, never a subdomain or a path |

| Agent or leaked SDK key reports false model use (hides spend, or floods the roll-up) (B4a) | Numbers are labelled "estimated from what the agent's SDK reported" and never used to refuse; per agent and day at most 50 distinct models (rest folded into "(other)"), 35-day window, future spans count as now, token counts above 1,000,000,000 per side ignored, sums capped on read; roll-up holds counts and model names only (no prompt, completion or thought text) | An SDK key can name any agent of its organization, and an SDK that under-reports shows less: spend is not authoritative until a proxy (B5) exists |
| Model or provider names from an agent shown in the dashboard or chat (B4a) | Names are length-bounded (64 and 128) and shown as plain text only (control and bidirectional characters replaced, React escapes markup); alerts carry the agent's registered name and counts, never a model name | None known |
| Spend limit relaxed to silence alerts (B4a) | Admin only, audited, confirmation to raise or remove, compare-and-set against the state the decision was made on | An admin can still turn the alert off |
| Approved-model list weakened or cleared to hide an unapproved model (B4b) | Admin only, audited, compare-and-set on a version, clearing needs confirmation; at most 50 entries of plain names | An admin can still clear it |
| A hostile model name reaches the dashboard or a chat through a RAD-MDL-001 finding (B4b) | The database reduces names to `[a-z0-9_.:/-]` and 128 characters before storing; the dashboard renders text only; alerts carry the stored name | None known |
| Model proxy prototype (B5, off by default): a stolen agent token, a frozen or foreign agent, a model outside the passport, a hostile request body, a hostile or stalled provider, the provider key reaching an agent or a log | Same token verifier and passport cache as the tool route; status, token version and a `model` scope are checked before anything is sent; request, response and stream sizes, idle and total timeouts are bounded; the agent's token and cookies are never forwarded and the response headers are an allowlist; a provider 401 or 403 becomes a bare 502; usage is counted from the provider's own answer; no prompt or completion text is stored or logged; every refusal happens before the provider call | One deployment-level provider key in an environment variable (per-tenant key custody is not built); a stream can carry customer content through the gateway (not stored); an agent holding the provider key can bypass the proxy; no inspection of content |
| A holder of the gateway's service token reports usage for an agent that is not theirs, or floods the measured table (B5b) | `POST /internal/v1/model-usage` takes the service token only (the same trust as the gateway's other reports); the organization is taken from each agent's own row and never from the payload (the field is refused); rows are validated one by one and a bad row is rejected on its own; at most 500 rows a batch; a batch id seen in the last 7 days counts once; 50 models per agent and day, the rest folded; a time in the future counts as now and one older than 35 days is dropped; measured usage is never added to the SDK-reported figure | The service token is a deployment-level credential: whoever holds it can add measured usage for any agent of any organization (it cannot read or remove any); nothing refuses a call on this figure until B5c |
| An agent keeps spending past its daily limit through the model proxy, or the limit check is skipped (B5c) | The proxy refuses at or over the limit using MEASURED usage only (never what an SDK reports), before the provider is called; a limit it cannot check fails closed (unpriced model or tokens, malformed limit = 0, unreadable table = 503, a core without the field = lookup fails and the call is denied); no limit means no check | Cost is known only after a call ends and reaches the proxy a few seconds later (batch report interval + core + 2 s cache), so calls in flight and in that lag can overshoot, each bounded by max_tokens; an agent holding the provider's key can bypass the proxy entirely (RedHand controls only what flows through it); refusals are not yet written to the Black Box |
| SDK key used to mint cloud credentials for an agent it does not own (route sweep, 2026-11-17) | `/v1/iam/mint/*` now needs a passport of the key's own organization that is active and not reported-only, and a tool its scopes cover; unknown, foreign and unusable agents get the same 403; a failed lookup refuses | The broker still uses one deployment-level source credential for all organizations; per-tenant source credentials and cloud-side account binding are not built |
| Stolen or leaked organization SDK key (C1a) | Keys are issued by an admin and shown once, stored as SHA-256 only, expire (default 90 days), can be revoked at once (audited), 10 active per organization, per-key ingest limit, "last used" visible; nobody can write the key table directly | A holder can report for any agent of the organization until it is revoked; C1b removes its power to rename passports or create usable ones |
| SDK key holder renames a passport or creates one that can reach tools (C1b) | Ingest never updates an existing passport except its heartbeat; a new agent id becomes a "reported only" passport refused at token exchange, reported as frozen to the gateway and skipped by the Risk ladder until an admin promotes it (confirmed, audited, admin-only, tenant-scoped) | The holder can still create reported-only rows (bounded by the per-key limit) and send false telemetry for existing agents; spend and risk numbers stay self-reported |
| A stranger creates organizations or joins one uninvited (D1) | Creating needs a single-use, expiring, hashed sign-up code the platform owner issued (192 random bits; unknown, used and expired give one answer; `SIGNUP_MODE=closed` refuses everyone); joining needs a single-use invite token an admin issued (never owner, up to the inviter's role, revoked or expired or from a demoted inviter is dead); both attempt routes are limited per person and per source before any lookup; one organization per person; every step audited without the secret | Open sign-up is not offered; a leaked code or invite link is usable by whoever holds it until it is used, revoked or expires (send them privately); an invite link is a bearer credential for its role |
| Data leaves through the export, or a hijacked owner deletes the organization (D1 PR 3) | Export is owner-only, audited in the same transaction (counts, never the data), one per hour per organization (durable, checked against the audit log), secret columns are left out where the data is read and a SQL test fails when a secret-looking column is not excluded or a tenant table is missing from the manifest; deletion needs the owner role and the address name typed back, freezes agents and switches SDK keys off at once, leaves 7 days to cancel, answers 403 to everything but status, export and cancel meanwhile, and the purge is not an API route (database owner only, refuses before the grace period, rolls back unless every table is empty for the tenant) | A hijacked owner session can still export (once an hour) and start a deletion; the audit rows and the owner's own alerts are the detection, and no notification is added by this change; a database backup keeps deleted data until it ages out |
| An admin escalates themselves or removes the last owner (D1) | The database functions refuse a role above the actor's, a change to someone above them, an owner made by anyone but an owner (confirmation required), and removing or demoting the last owner; all audited | An owner can remove other owners (two owners can lock each other out down to one, never to zero) |
| A viewer or operator reads agent reasoning or tool-argument text through the dashboard snapshot, or issues agent credentials (D1) | The snapshot omits those fields for viewers; registering an agent and rotating a key need admin | Security operators and above still see the trace text (they investigate incidents) |
| Admin abuses key management (C1a) | Every create and revoke is audited (actor, time, name, prefix; never the hash) | An admin can issue a key; the audit log shows it |
