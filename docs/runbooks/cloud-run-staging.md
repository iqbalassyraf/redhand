# Runbook: staging on Google Cloud Run

Deploys **redhand-core** and the **AgentWall gateway** to Cloud Run in `asia-southeast1`,
using the staging Supabase project. Files: `deploy/cloudrun/` (`Dockerfile.core`,
`Dockerfile.gateway`, `cloudbuild.yaml`, `deploy.sh`, `smoke.sh`).

Status: the scripts and Dockerfiles were checked locally (shellcheck, syntax, and a runtime-only
dependency install that starts both apps in staging mode). They have **not yet run against Google
Cloud**; the first deploy may need small fixes (see Troubleshooting).

## What gets created

| Resource | Name | Notes |
|---|---|---|
| Cloud Run service | `redhand-core` | 1 vCPU, 512 MiB, min 0 / max 1 instance, public URL |
| Cloud Run service | `redhand-gateway` | same sizing, public URL (agents authenticate with their own token) |
| Secrets (Secret Manager) | `redhand-supabase-secret-key`, `redhand-internal-service-token`, `redhand-agent-token-signing-key` | the last two are generated by the script and never shown |
| Service accounts | `redhand-core-sa`, `redhand-gateway-sa` | no project-level roles; each can read only its own secrets |
| Artifact Registry repo | `redhand` | one image per service, tagged with the git commit |

Cloud Run's own "invoker" check is off (`--allow-unauthenticated`) because browsers and agents call
the services directly; every request is authenticated by the application. Min 0 instances means no
cost while idle; the first request after idle takes a few seconds. Max 1 instance is deliberate:
stream tickets and rate limiters live in process memory.

## Deploy

1. Have ready: the Google Cloud project ID, and the Supabase **secret key**
   (Supabase dashboard → project → Project Settings → **API Keys** → *Secret keys*; if that kind
   is rejected later, the *Legacy API Keys* tab has `service_role`).
   On macOS the built-in `openssl` may not support Ed25519; the script then tries Homebrew's
   OpenSSL 3 and Python's `cryptography` package, and stops with instructions if neither works
   (`brew install openssl`). It never stores an empty or malformed key.
2. From the repository root on your computer:

```bash
gcloud auth login
```

```bash
gcloud config set project project-d0dac5d1-c415-4b94-94e
```

```bash
SUPABASE_URL=https://qxxiksevqfmkqstrdkxi.supabase.co deploy/cloudrun/deploy.sh all
```

The script shows the account and project and asks to continue. It asks once for the Supabase key
(hidden input) and sends it straight to Secret Manager. It builds both images in Google Cloud
(about 3-6 minutes each), deploys core, then the gateway.

3. Run the smoke test with the two URLs the script prints:

```bash
deploy/cloudrun/smoke.sh <core-url> <gateway-url>
```

Every line should say PASS.

After the dashboard has a URL, allow it in both services:

```bash
SUPABASE_URL=https://qxxiksevqfmkqstrdkxi.supabase.co DASHBOARD_ORIGIN=https://<dashboard-url> deploy/cloudrun/deploy.sh cors
```

## Check it in the Google Cloud console

Open https://console.cloud.google.com and make sure the project selector (top bar) shows your
project.

1. **Cloud Run** (menu → Cloud Run). Both services show a green tick. Click `redhand-core` →
   *Revisions*: the newest revision serves 100% of traffic. *Logs* tab: look for
   `Application startup complete`. A red cross means startup failed; the log says why (usually a
   missing or unreadable secret).
2. **Secret Manager** (menu → Security → Secret Manager). Three secrets, each with one enabled
   version. Click one → *Permissions*: only the matching service account(s) appear.
3. **Artifact Registry** (menu → Artifact Registry → `redhand`). Two images, tagged with the commit.
4. **Cloud Build** → *History*: the two builds succeeded.
5. **IAM & Admin → Service Accounts**: `redhand-core-sa` and `redhand-gateway-sa` exist.
6. **Billing → Budgets & alerts**: a budget alert exists (suggest USD 5). **Cloud Run → service →
   Metrics → Instance count** should drop to 0 when nobody is using it.

## First login test (confirms the token issuer)

Core expects tokens whose `iss` is `https://qxxiksevqfmkqstrdkxi.supabase.co/auth/v1`. This could
not be checked before deploy. When the dashboard is up and you sign in: success confirms it. A 401
means a mismatch; see `docs/runbooks/operators-get-401.md`. Core's log line `Operator token
rejected: ...` names the reason; the fix is one environment variable:

```bash
gcloud run services update redhand-core --region asia-southeast1 --update-env-vars OPERATOR_JWT_ISSUER=<value from the token>
```

## Troubleshooting

| Symptom | Likely cause and fix |
|---|---|
| Build fails with a permission error (Artifact Registry, logs or storage) | In new projects the Cloud Build identity may lack roles. In IAM, grant the Cloud Build service account (or the Compute Engine default service account, whichever the error names) `Artifact Registry Writer`, `Storage Object Viewer` and `Logs Writer`; then re-run. |
| `deploy.sh` refuses `--allow-unauthenticated` | An organization policy forbids public services. Ask whoever manages the Google Cloud organization, or tell me and we will front the services differently. |
| Core revision fails to start | Cloud Run → service → Logs. `Operator authentication is not configured` or a settings error: an environment variable is missing. A secret error: the service account cannot read it (re-run `deploy.sh secrets`). |
| Smoke test: database check returns 500 | Core could not use the Supabase key. Try the *Legacy API Keys* `service_role` key: Secret Manager → `redhand-supabase-secret-key` → *New version*, paste it, then Cloud Run → `redhand-core` → *Edit & deploy new revision* (or re-run `deploy.sh core`). |
| Smoke test: JWKS check fails | `AGENT_TOKEN_SIGNING_KEY` is missing or unreadable by `redhand-core-sa`. |
| First request very slow, then fine | Cold start (min instances 0). Expected. |
| `/healthz` returns 404 on the `*.run.app` address | Cloud Run's front end can intercept that path. Use `/health` (served by both services). |

## Rollback and teardown

- **Roll back:** Cloud Run → service → *Revisions* → *Manage traffic* → send 100% to the previous
  revision. Secrets keep their versions.
- **Stop serving:** delete the two services (Cloud Run → select → *Delete*). Secrets, images and
  service accounts remain; delete them separately only if you are sure.

## Known limits of this staging setup

- The gateway's tamper-evident audit ledger is in memory and is lost on each restart (Cloud Run's
  disk is not persistent); moving it to the database is Phase 3.
- Single instance per service; no multi-region; no custom domain yet.
- Only MCP servers reachable over public `https` can be used (the gateway blocks private
  addresses by design).
