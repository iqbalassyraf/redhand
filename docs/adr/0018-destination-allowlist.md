# ADR 0018: Per-agent destination allowlist (addresses in tool-call arguments)

**Status:** Accepted (2026-11-13). Phase 4 M7, new done test 11, decisions F-D2 and D10. Plan: `docs/plans/phase4-m7-destination-allowlist.md` (on PR 58). Builds on ADR 0015 (the Radar only observes), ADR 0017 (loop detection, whose findings path this reuses) and the threat model.

## Context
The Radar can only watch. A hijacked or prompt-injected agent that has a legitimate tool (send an email, post a webhook, fetch a URL) can send customer data to an address the attacker chose, and nothing in RedHand could stop it. The one Phase 4 control that can **prevent** data leaving is a per-agent list of the hosts that agent may name in a call.

## Decision
1. **What is checked.** The web addresses (`http`, `https`, `ftp`, `ftps`, `ws`, `wss`, `sftp`) and email addresses an agent **wrote** into a tool call's arguments (string values and object keys, at any depth), by pure functions in `agentwall/src/firewall/destinations.py`. No DNS, no I/O. The tool name and results are not read. Scheme, port, path and query are ignored. Matches are exact hosts: `sub.example.com` is not `example.com` (no wildcards in v1, because without a public-suffix list `*.co.uk` or `*.github.io` would allow strangers, and a new dependency needs separate approval).
2. **Parsers disagree, so one URL is a set of candidate hosts.** The authority is read the strict way (ends at `/ ? #`) and the browser way (also ends at a backslash, and extra slashes after the scheme are ignored, so `http:///evil.com` and `http:\\evil.com` count), before and after the first and the last `@`. A destination is allowed only if **every** candidate is on the list; a candidate that cannot be normalized is never allowed (an ambiguous URL such as `http://a@b@good.com/` is refused). `http://good.com\@evil.com`, `http://good.com@evil.com`, `http://evil.com#@good.com`, an encoded `%40`, IPv4 as one number, hex or octal, IPv6 and IPv4-mapped IPv6, and a Cyrillic look-alike letter are all covered by tests.
3. **One canonical spelling.** `normalize_host` percent-decodes once, applies NFKC, lower-cases, strips trailing dots, converts to IDNA (punycode), parses every IPv4 number form itself (the operating system's parser differs by platform) and folds IPv4-mapped IPv6 to IPv4. Core must not import the gateway, so core has a copy; `agentwall/tests/test_destination_normalizers_in_sync.py` runs the same 67 vectors through both and fails if the source text or character tables differ.
4. **Modes per agent:** `off` (default), **observe** (records a `RAD-DST-001` finding, never refuses), **enforce** (also refuses the call). Enforce **refuses what it could not check** (arguments past the 64 KiB, 1,000-value, depth-16, 200-match or 50-distinct-destination budget), so a call is never allowed on the strength of text that was not read. Any unexpected error in enforce denies; in observe it is counted and changes nothing. The refusal message and data echo nothing from the call.
5. **A finding keeps only the coarse host** (the last two labels; `ip-address` or `unparseable` otherwise), in a new nullable `security_findings.detail` column validated by the API and by a table check, because a subdomain can carry the stolen data. Without a public-suffix list `a.b.example.co.uk` keeps `co.uk`: less than ideal, but never more than the registrable part. The first host seen in a 5-minute window is kept. Findings reuse the Radar's storage, review, suppression, retention and a 10-minute alert cooldown of their own.
6. **Who changes it:** admin only, audited (`passport.destination_added`, `_removed`, `_mode_changed`). **Adding a host, turning enforcement on and turning the check off each need an explicit confirmation**; enforce needs a non-empty list; the last host cannot be removed while the agent enforces; the mode change is compare-and-set on the mode the caller saw; at most 100 hosts per agent, enforced in SQL; tenant checks in SQL and in core.
7. **Fail closed on the settings.** Core sends `destination_mode` and `allowed_destinations` as required fields (the list only while the mode is not `off`); the gateway validates them strictly (three modes, entries in canonical form, at most 100). An older core or a malformed value makes the lookup fail and the call is denied. In core, a missing mode is `off`, a mode that is present but not one of the three reads as **enforce** (the restrictive reading), a stored entry that does not normalize to itself is dropped (fewer allowed, never more), and a failed list lookup is a 503.
8. **Order on the hot path:** after scope, tool pin and guardrails, **before the loop check and Budget Guard**, so a refused call consumes neither. Kill switch: `AGENTWALL_DESTINATION_CHECK_ENABLED=false` on the gateway skips the check for everyone.

## Alternatives considered
One list per organization (one agent's needs would widen every agent). Wildcards or registrable-domain matching with a public-suffix list (a dependency, and shared-hosting suffixes invite mistakes; deferred). Resolving DNS and comparing addresses (slow, an outbound call on the hot path, unreliable under rebinding). An existing URL library (libraries disagree with each other, which is the attack; the candidate-set approach is deliberately stricter than any one parser). Allowing a call whose address cannot be parsed (rejected: unparseable is flagged and refused in enforce).

## Consequences
- **Not covered, and stated in the dashboard, runbook and threat model:** an address written as a bare word (`evil.com`), encoded (base64), split across fields or built by the tool; what a tool does with the data after it is called; calls outside the gateway. Scheme and port are ignored, so an allowed host on another port or protocol is allowed. A URL that is not a destination (a search query that contains a link) is flagged and, in enforce, refused, which is why observe comes first and the list is per agent.
- Authoring a list blind is hard: observe shows only the coarse host. Offering "add to the allowed list" from a finding needs a privacy decision about storing full hosts and is a follow-up.
- Deploy order: migration, core, gateway, dashboard. Rollback: the down migration (deletes every allowlist, destination findings and `RAD-DST` suppressions), after redeploying the previous gateway.

## Measured cost (in process, instant fakes, warm cache; staging confirms)
`destination_check` averages 15 microseconds for a call with no address and 55 to 80 for one with an address; 0.26 ms for 4 KiB of text with an address; 0.14 ms for 64 KiB of plain text; hostile worst cases (64 KiB of back-to-back `http://`, thousands of addresses) about 5 ms because of the match cap. The first version cost 3.7 ms on 64 KiB of plain text and 31 ms on thousands of addresses; two cheap substring prechecks and a shared cap on matches fixed both. Budget: p50 10 ms, p99 50 ms.

## Differences from the approved plan
- Turning the check **off** also needs the confirmation (the plan named adding and enforcing), as for the Radar and loop switches.
- The last host cannot be removed while enforcing (the plan only said enforce needs a non-empty list at the moment of switching).
- A present-but-unrecognised mode reads as enforce in core; a failed list lookup is a 503; non-canonical stored entries are dropped (the plan said nothing).
- A shared cap of 200 URL and email matches per call (beyond it the call is `untracked`) and substring prechecks were added after measuring.
- Browsers' acceptance of `http:///evil.com` and `http:\\evil.com` is handled (found while writing the tests).
- `RadarScanner.report_loop` is now a thin wrapper over a general `report_finding`; its behaviour and tests are unchanged.
- The SQL tests share one database, so the new SQL test runs in a rolled-back transaction (the M6 test had to be fixed the same way after its CI run failed).
- `scripts/benchmark_gateway.py` was not extended (its repair is PR 61); the numbers above come from an in-process script using the test harness.
